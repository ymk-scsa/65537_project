# Apple 版（apple_branch）の追加内容

`apple_branch` で追加した、次の 4 つについてまとめます。

1. 新しいニューラルネットワーク **RayGraph ハイブリッド**（`model/apple_net.py`）
2. **先手・後手で評価を変える**しくみ（共通の胴体 + 手番別の頭）
3. 探索の **C++ 版**（`search/cpp/`）。Python 版はそのまま残してあります。
4. **高速化・軽量化**（CPU だけで動かす前提）

---

## 1. RayGraph ハイブリッド（`appleXS` / `appleS` / `appleM`）

これまでのモデルは「CNN・GNN・Transformer のブロックを順番に積む」形でした。
RayGraph では、**将棋の駒の動き方そのものを、ネットワークの形として組み込みました。**

| 部品 | 中身 | 将棋での意味 |
|---|---|---|
| Local（CNN） | 3x3 の深さ方向畳み込み + 点ごとの MLP | 金・銀・玉など「近くの形」 |
| **RayCast**（新しく考えた部分） | 8 方向の「光線」に沿った伝達。マスごとに**透明度**を学習し、駒があると光がさえぎられる | 飛・角・香など**走り駒の利き**。駒にぶつかると利きが止まることを、微分できる形で表す |
| **MoveGraph**（GNN） | 玉の 8 近傍 + 桂の跳びでつながるグラフ。送り元の駒の種類からゲートを学習 | 「この駒はこの方向に利きがあるか」を学ぶ**利きグラフ** |
| Global（Transformer） | 81 マスの自己注意を最後に 1 層 | 盤全体のつながり |

この Local → RayCast → MoveGraph を 1 ブロックとして繰り返し、最後に Global を通します。

RayCast は、線に沿った漸化式 `m(j) = v(j+1) + γ・τ(j+1)・m(j+1)` で計算します。
4 系統（筋・段・斜め・逆斜め）× 前後 2 方向 = 104 本の線をまとめて処理するので、軽く動きます。
総当たりで計算した値と一致することをテストで確かめています（誤差 1e-7 程度）。

| モデル | チャンネル | ブロック | 注意層 | パラメータ数 |
|---|---|---|---|---|
| appleXS | 48 | 3 | なし | 約 0.09M |
| appleS（標準） | 64 | 4 | あり | 約 0.23M |
| appleM | 96 | 6 | あり | 約 0.63M |

参考: 今までの modelC は約 18.4M、fastA は約 6.7M です。

## 2. 先手・後手で評価を変える

- **胴体は共通**です。入力に手番の埋め込みを足しています。
- **方策**は、共通の出力に手番別の補正を足します。
- **価値**は、手番ごとに「勝ち / 引き分け / 負け（WDL）」の 3 つを出します。
- 探索に渡す値は「勝ち点の期待値」から作ります。
  `E = P(勝) + d × P(引き分け)`、`value = 2E − 1`
  `d` は電竜戦のルールに合わせて**先手 0.4・後手 0.6**です（変更できます）。
- 探索の中の千日手・最大手数（512 手）による引き分けも、同じ手番別の値で扱います。

学習（`train/supervised_train.py`）は、apple 系のモデルなら自動で WDL の学習に切り替わります。
HCPE では対局結果をそのまま WDL の目標にし、PSV では評価値から勝ち・負けの確率を作ります。

### Python 版から変えたところ

- 盤面を毎回 sfen 文字列から作り直すのをやめ、指し手を進める・戻す方式にしました。
- 葉の局面を `batch_size` 個ためてから、NN にまとめて渡します（バーチャルロス方式）。
- 終局判定を足しました: 詰み、千日手（手番別の引き分けの値、連続王手）、最大手数、入玉宣言（27 点法）、葉での 1 手詰め。
- ルートで df-pn の詰み探索をし、入玉宣言できるときは `win` を返します。
- **MCTS の符号を直しました。** Python 版 `mcts.py` は、相手から見た値で手を選んでいました。`mcts.py` 側も 1 行直しています。
- 特徴量と指し手ラベルは、Python 版（`game/board.py`）と**完全に同じ**です。24 万手以上で一致を確認しました。
- NPLS は Python 版の計算方法をそのまま移植しました。最後の手の選び方は「訪問回数だけ」で、価値を使いません。このため、駒をタダで取れる局面でも取らないことがあります（材料の損得だけで評価する簡単なテストで確認）。強さを求めるなら MCTS をおすすめします。

### 電竜戦向けの時間の決め方（`--time_mode denryu`）

電竜戦では、1 手の消費時間は **1 秒未満切り捨て** で、そのあと 2 秒加算されます。
そこで、思考時間を「k 秒 + (1000 − margin) ミリ秒」にそろえます。
たとえば 2.6 秒考えても消費は 2 秒で、すぐ 2 秒戻るので、持ち時間は減りません。

| 状況 | 思考時間 |
|---|---|
| 先手・残り 180 秒 | 6.6 秒 |
| 後手・残り 600 秒 | 17.6 秒 |
| 残り 20 秒 | 2.6 秒（持ち時間が減らない） |

`margin`（既定 400ms）は通信の遅れの分の余裕です。サーバーとの通信で一度テストしてから決めてください。

## 5. GPU 向けの合法手生成（ビットボード演算）

NN の入力（447bit 特徴量）から、**N 局面分の合法手をまとめて**作ります。
すべて PyTorch の整数演算なので、CPU でも GPU（CUDA）でもそのまま動きます。

| ファイル | 中身 |
|---|---|
| `game/gpu_bitboard.py` | **本命**。81 マスを 64bit 整数 2 つに詰めたビットボードで、シフト・AND・OR だけで計算する |
| `game/gpu_bitboard_flat.py` | 実験。成りの前処理（グループ × 敵陣の内外への複製）をやめたビットボード |
| `game/gpu_movelist.py` | 実験。盤面状のテンソルをやめ、駒があるマスだけのリストで計算する（CUDA 専用） |
| `game/gpu_movegen.py` | 同じことをマス単位（81 個の bool）で書いた、読みやすい版（正しさの基準） |
| `play/bench_movegen.py` | cshogi との一致と、上の 3 実装の速さの比較 |

```python
from game.gpu_bitboard import legal_move_mask_bb
mask = legal_move_mask_bb(features)        # (N,447) → (N,2187) の bool。方策ラベルごとに合法なら True
logits = logits.masked_fill(~mask, -1e9)   # 合法手だけで softmax を取れる
```

### しくみ

- 自分の駒の 10 方向（8 方向 + 桂の 2 方向）を「方向の次元」としてまとめて、1 回の演算で計算します。方向ごとにシフト量が違うので、要素ごとにシフト量を変えられる torch のシフト演算を使っています。
- 走り駒の利きは、Kogge-Stone 法（1・2・4 マスずつのシフト 3 回）で広げます。
- 成り・不成の扱いが同じ駒を 7 グループにまとめ、さらに「元のマスが敵陣か」で分けます。こうすると、成れるかどうかを駒 1 つずつ見なくても判定できます。
- 王手・ピンは、自玉から 8 方向に光線を伸ばして、1 つ目・2 つ目の駒を見て調べます。
- 打ち歩詰めは、候補の局面だけを相手の立場で作り直し、同じ関数で「相手に合法手があるか」を調べます。
- 方策ラベル（`dir*81 + to`）と合法手は 1 対 1 に対応します。走り駒は途中で止まるので、同じラベルになる手は 1 つしかありません。そのため、出力をそのまま方策のマスクに使えます。

### 実験版と、元のビットボード版の違い

3 つとも入力は `(N, 447)`、出力は `(N, 2187)` の bool です。マス番号と方向番号は方策ラベルと同じなので、GPU 上のロジットへそのまま掛けられます。学習の本線（`--mask_illegal`）が呼ぶのは、今も `legal_move_mask_bb` です。フラット版と駒リスト版は、同じマスクをより少ない仕事で出すための実験です。

**フラット版**（`legal_move_mask_flat`）は、成り判定の規則はそのままに、走りを広げる前の複製をやめたものです。元の版は、成りをシフトと AND だけで書くために、駒を「7 グループ × 敵陣の内か外か」へ複製してから Kogge-Stone で広げます。ほとんどの面は全ビット 0 でも、シフトのたびに読み書きされます。フラット版は「方向 × 実際にその向きへ動く駒種」だけをずらします。成りは、元のマスが敵陣であるビットを駒と一緒に運び、広げたあとで「元か先が敵陣なら成れる」と足します。減ったのは、中身が空の面のシフトです。PyTorch の整数演算のままなので、CPU でも GPU でも動きます。

**駒リスト版**（`legal_move_mask_list`）は、データの持ち方を変えたものです。81 マスの面を方向ごとに持つのをやめ、1 ワープの各レーンが 1 局面を持ちます。81 マスを 1 回走査して、歩・香・桂・銀・金相当（金・と・成香・成桂・成銀）・角・飛・馬・龍のリストへ、駒があるマス番号だけを詰めます。ループはそのワープの中で一番多い枚数で止まります。相手の利きと王手は、レーンの中の短いビットセット（27bit が 3 つ）のままです。実装は Triton のカーネルで、CUDA だけで動きます。`torch.compile` は使いません。

| | 元のビットボード | フラット | 駒リスト |
|---|---|---|---|
| データの形 | 方向 × グループ × 敵陣の内外のビットボード | 方向 × 動く駒種のビットボード | 種類ごとのマス番号リスト |
| 成り | 複製した面の AND | 敵陣ビットを一緒にずらしてから足す | マスの段を見て判定する |
| 空のマス | 面の中の 0 ビットは安い。空の面のシフトは残る | グループ × 内外の空の面をやめた | リストに入れない |
| 実行 | CPU / GPU。`--compile` で融合 | 同じ | CUDA の 1 カーネル |

速さは RTX 3060 で、ランダムな 780 局面を繰り返したバッチです。ビットボード版とフラット版の compile は `torch.compile` の `mode=default`。打ち歩詰めの除去を含みます。数字はならしのあとの定常速度です。

| バッチ | ビットボード + compile | フラット + compile | 駒リスト |
|---:|---:|---:|---:|
| 4,096 | 604,000 局面/秒 | — | 1,197,000 局面/秒 |
| 32,768 | 1,431,000 局面/秒 | 1,541,000 局面/秒 | 5,751,000 局面/秒 |
| 131,072 | 1,556,000 局面/秒 | 1,677,000 局面/秒 | 7,363,000 局面/秒 |

バッチ 4,096 のフラット版は、計測の中に別の形の再コンパイルが混ざったので載せていません。大きいバッチでは、フラット版が元のビットボード版を少し上回り、駒リスト版は元の約 4.7 倍です。`compile` する前の eager では、フラット版はバッチ 4,096 だと元より遅く、バッチ 13 万では元の約 1.2 倍（毎秒約 79 万対 65 万。こちらは初期局面の繰り返し）でした。融合でカーネル起動が消えると、フラット版の有利が出ます。

正しさは、フラット版が元のビットボード版および cshogi の LegalAll と一致すること、駒リスト版がランダムな 2325 局面で `all_moves` のありなしとも元のビットボード版と不一致 0 であることです。測り直しは `python play/bench_movegen.py --device cuda --compile` です。

### 正しさ

cshogi の `legal_moves`（LegalAll）と比べて、**のべ約 14 万局面・600 万手以上で不一致 0** でした。
王手されている局面は約 1.5 万、打ち歩詰めで手が消える局面は 52 あり、どちらも含めての結果です。
`all_moves=False` にすると、意味の薄い不成（成れるときの歩・角・飛の不成など）を省いた手だけになります。

### 速さと、正直な見込み

| 方法 | 局面/秒 | 備考 |
|---|---|---|
| cshogi の C++（1 コア） | 約 92 万 | 方策ラベル化込み。こちらの CPU で測定 |
| cshogi（Python から 1 局面ずつ） | 約 3.3 万 | 方策ラベル化込み |
| ビットボード版（CPU 2 スレッド、batch 4096） | 約 1.6 万 | CPU では C++ にかなわない |
| ビットボード版（GPU、compile） | 約 60 万〜156 万 | RTX 3060。上の比較表（batch 4,096〜131,072） |
| 駒リスト版（GPU） | 約 120 万〜736 万 | 同じ条件。batch 131,072 で毎秒約 736 万 |

- 上の比較表が、この PC（RTX 3060）での測定です。batch 13 万では、compile したビットボード版が毎秒約 156 万、駒リスト版が毎秒約 736 万です。
- ただし、**今の C++ 探索（MCTS）に組み込んでも、ほとんど速くなりません**（確信度 85）。今は時間の 98% 以上が NN の推論で、合法手生成は 1〜2% しか使っていないためです。また、CPU 版の cshogi も十分速いです。
- 大きく効くのは、**盤面の更新も含めて、探索を全部 GPU に載せる場合**です。たとえば、何千局もの自己対局を GPU でまとめて回す強化学習などです。JAX で書かれた Pgx というライブラリが、将棋でこの方式をとっています。
- **今すぐ使える使い道**: 学習のときに、合法でない手を方策の学習から外せます（`--mask_illegal 1`）。CPU での学習でも、余分にかかる時間はほぼありません（こちらでは 35.4 秒 → 33.8 秒で、誤差の範囲）。強さへの効果は、本物の棋譜で学習して確かめる必要があります。

```bash
# GPU のある PC で
python play/bench_movegen.py --device cuda
python play/bench_movegen.py --device cuda --compile
# 学習で合法でない手を外す
python train/supervised_train.py --mode appleS --mask_illegal 1 ...
```
